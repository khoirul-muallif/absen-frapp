## Ganti password: scope dipersempit, dan itu keputusannya

Item lama berjudul "ganti email & password". Separuhnya dibuang: email tidak
dipakai untuk login (username sejak fase 79), tidak dipakai untuk reset
(ditolak fase 78 karena karyawan RS belum tentu bisa mengakses email kerjanya),
dan sejak fase 81 ~110 dari 150 karyawan memang tidak punya. **Mengedit field
yang tidak melakukan apa-apa bukan fitur.**

Backend `login()` ternyata sudah menghapus SEMUA token lama tiap login —
aplikasi ini single-session by design. Jadi pertanyaan "cabut token lain setelah
ganti password?" gugur sendiri: tidak pernah ada token lain.

Yang mengunci risiko hash ganda bukan test `Hash::check()`, tapi test kedua yang
benar-benar login pakai password baru. Hash ganda bisa lolos pemeriksaan yang
salah arah; tidak pernah lolos login sungguhan.

Sempat dikira endpointnya sudah ada di backend. Yang sudah ada ternyata **reset
password oleh admin dari panel Filament** (fase 78) — admin-side, bukan API, dan
gampang ketuker.

## Tab Informasi: modul pertama yang pakai paging

Backend siap sejak fase 75, FE-nya masih hardcoded empty state.

`InformasiHalaman` membawa info paging dari akar `data`, jadi "masih ada lagi?"
dibaca langsung, bukan ditebak dari jumlah record. Model list dan detail
DIPISAH: `index()` mengirim `ringkasan` (accessor `Str::limit` 150 di model
backend) dan `show()` mengirim `isi` penuh — bukan subset satu sama lain.

Pencarian pakai debounce 400ms plus penjaga `_requestTerakhir`, pola yang sama
dengan RiwayatScreen. Penjaga yang sama dipakai saat memuat halaman berikutnya,
supaya baris kata kunci lama tidak menempel di bawah hasil yang baru.

404 di layar detail ditangani khusus: `findOrFail` ada DI DALAM scope `aktif()`,
jadi 404 biasanya berarti admin menonaktifkan pengumuman itu sementara daftarnya
terbuka. Tombol "Coba Lagi" tidak menolong, jadi yang ditawarkan "Kembali".

Sempat dikira `ringkasan` bug karena `git grep "ringkasan"` di model tidak kena
— ternyata accessor-nya pakai gaya lama `getRingkasanAttribute()`. Tinker
membuktikannya jalan.

## Logo instansi: simpan lokal, bukan endpoint publik

Masalah urutannya: LoginScreen dan SplashScreen tampil sebelum ada yang login,
jadi aplikasi belum punya token maupun data user.

Dipilih **simpan lokal setelah login pertama**, walau jawaban "selamanya satu
instansi" sebenarnya membuat endpoint publik sah. Alasannya: endpoint publik
tanpa cara memilih instansi memaksa asumsi instansi tunggal masuk ke API —
asumsi yang justru ingin dihindari. Harganya cuma layar login pertama di
instalasi baru, sekali seumur pemakaian.

`InstansiStorage` SENGAJA tidak dibersihkan saat logout, beda dari
`TokenStorage`. Nama dan logo instansi bukan data rahasia, dan menghapusnya
berarti karyawan yang logout lalu login lagi kembali melihat placeholder.
**Jangan "dirapikan" dengan menambahkannya ke `AuthService.logout()`.**

Nama instansi ikut disimpan, bukan cuma logo: LoginScreen sebelumnya menulis
"RSU Banyumanik 2" sebagai teks hardcoded. Tanpa ini asumsi instansi tunggal
cuma pindah tempat, dari API ke layar.

`FlutterLogo` di SplashScreen akhirnya hilang.
